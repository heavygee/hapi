## Blocker

### B1 — Hub accepts a request-body `sourceSessionId` as the authoritative stored provenance

**Evidence:** `hub/src/web/routes/messages.ts:14-17` (header check), `:23-42` (`resolveTrustedPeerMeta`), `:151-160` (call site); wire field at `shared/src/apiTypes.ts:512-517, 529`.

The only thing separating "peer delivery" from "operator keystroke" is a client-set request header, and the only thing constraining *which* peer you claim to be is that the id exists in your own namespace:

```ts
const peerDelivery = isPeerDeliveryRequest(c)          // client-set header
const peer = peerDelivery
    ? resolveTrustedPeerMeta(engine, c.get('namespace'), parsed.data.peer)  // client-set body id
    : undefined
```

`resolveTrustedPeerMeta` verifies existence and namespace, then persists the claim verbatim. There is no binding between the caller and the session it names. The hub's own auth carries no client-kind claim — the JWT payload is namespace-only (`hub/src/web/middleware/auth.ts:42`, minted from an access token at `hub/src/web/routes/auth.ts:29-31`) — so a browser `fetch` from devtools, any script, or any agent that runs `hapi` (which re-reads the token from settings by design, `cli/src/agent/hapiSessionEnv.ts` "a fresh `hapi` re-reads settings") can attribute a message to *any other session in the namespace*.

The PR's own test is the proof: `hub/src/web/routes/messages.test.ts:279-311` constructs a request that is nothing but a header plus a chosen `sourceSessionId`, and asserts the hub stores it as provenance with a store-derived display name. Nothing in that request models the caller actually being that session. Agent A can therefore deliver a message that the UI renders as `@orchestrator` — the exact "forged authority" mode the issue exists to close, now with a UI chip vouching for it.

**Contract:** RFC kill criterion — "Client-supplied `sourceSessionId` in the request body is accepted as authoritative → stop (forged provenance is worse than none)"; issue scope-lock — "Accepting client-supplied `sourceSessionId` as authoritative → reject the PR".

The code comment at `shared/src/apiTypes.ts:507-510` half-acknowledges this ("the header is not a cryptographic authenticity bound") and then states something untrue in the same breath: "Authoritative source id is still never an MCP/tool argument". It is never a *tool* argument, but it is a request-body argument, which is what the kill criterion is about. `resolveTrustedPeerMeta` and `resolvePeerDeliveryProvenance`'s "Trusted peer provenance" docstring (`cli/src/modules/pingPeer/pingPeer.ts:28-32`) describe a guarantee the hub does not make.

**Two exits — orchestrator picks:**

1. **Bind the claim to an authenticated channel (satisfies the criterion as written).** The primary path already has the credential: MCP `ping_peer` executes *inside the source session's own CLI process*, which holds an authenticated `ApiSessionClient` for that session (`cli/src/claude/utils/startHappyServer.ts:294-304` calls `pingPeer({...})` with no identity, relying only on `process.env`). Deliver through that session's authenticated socket, or via a session-scoped `/cli/...` route, and have the hub set `sourceSessionId` from the authenticated connection while **ignoring the body field entirely**. A bare `hapi ping-peer` with no session client then falls through to unattributed, which is exactly contract item 3. Do not solve this by exporting a secret into the agent env — `cli/src/agent/hapiSessionEnv.ts` deliberately refuses that.
2. **Amend the contract, honestly.** If "namespace-verified claim" is accepted as the P0.5 bar, then say so: edit the RFC kill criterion and the issue scope-lock, delete the false sentence at `shared/src/apiTypes.ts:508-510`, rename `resolveTrustedPeerMeta` / the `resolvePeerDeliveryProvenance` docstring to say "claimed, namespace-verified", and reconsider whether the chip should look like a verified identity. Shipping exit 2 silently is the failure mode to avoid — the RFC already argues that a forgeable signal dressed as a contract is worse than no signal.

Confidence: 95% on the mechanism (demonstrated by the PR's own test and the namespace-only JWT). Severity follows the issue's explicit reject rule; downgrade requires exit 2 in writing, not a judgment call in review.

## Major

### M1 — The receiving agent still cannot see who pinged it

**Evidence:** `cli/src/api/types.ts:77-81` adds `peer` to `MessageMetaSchema`; nothing reads it. Every flavor forwards text only: `cli/src/kimi/runKimi.ts:101`, `cli/src/claude/runClaude.ts:385`, `cli/src/opencode/runOpencode.ts:244`, `cli/src/copilot/runCopilot.ts:143`, `cli/src/grok/runGrok.ts:82`, `cli/src/agy/runAgy.ts:291`. `cli/src/api/apiSession.ts:679-694` filters on `meta.sentFrom === 'cli'` and passes `UserMessage` through; consumers use `message.content.text` and `message.content.attachments`.

The RFC problem statement is "The recipient (**agent** + human UI) cannot tell peer delivery from operator keystrokes", and contract item 5 is "Receiving agents MAY reply with `ping_peer` targeting `meta.peer.sourceSessionId`". The human half shipped; the agent half did not. The agent receives a bare user message and has no id to reply to. The parsed-but-unread `peer` field in the CLI schema reads like an intention that never got wired.

Relying on the sender writing a prose `From:` line does not close this — the same RFC rejects prose headers as "forgeable social convention - useful dogfood, not a contract", and upstream `ping_peer` / `hapi ping-peer` do not add one.

**Suggested fix:** annotate the text handed to the agent for peer rows in one place. `formatMessageWithAttachments` (`cli/src/utils/attachmentFormatter.ts`) is called by every flavor, so a single machine-parseable line (e.g. `[peer session <id> "<name>"]`) covers all of them. **Caution:** `cli/src/agy/utils/agySessionScanner.ts:223` matches "the exact shape `formatMessageWithAttachments()` produces" — check that matcher before changing the helper, or thread `meta` to the runners instead. Either way, add a test that a peer-delivered message reaches the agent with the source id present.

## Minor

### m1 — Empty `peer: {}` written into every unattributed peer row, and sent on every request

`hub/src/web/routes/messages.ts:29-31` returns `{}` when there is no usable source; `hub/src/sync/messageService.ts:635-643` treats `{}` as truthy, so `:656` writes `peer: {}` into stored meta. On the client, `cli/src/modules/pingPeer/pingPeer.ts:378` always sends `{ text, peer }` even when `resolvePeerDeliveryProvenance()` returned `{}`. Fix: return `undefined` when nothing resolves, and omit `peer` from the CLI body when empty. Keeps stored meta honest and the wire minimal.

### m2 — Redundant cast loosens a typed field

`hub/src/web/routes/messages.ts:36`: `access.session.metadata as { name?: unknown } | null | undefined`. `Session['metadata'].name` is already `z.string().optional()` (`shared/src/schemas.ts:53-57`) and is read without a cast elsewhere (`hub/src/sync/syncEngine.ts:266`). The cast defeats strict TS and will keep compiling if the field is renamed. Fix: `access.session.metadata?.name` directly.

### m3 — Two dead locale keys after the post-freeze refactor

`message.peerFromSession` and `message.peerFromNamed` (`web/src/lib/locales/en.ts:14-15`, `web/src/lib/locales/zh-CN.ts:14-15`) were added at `02e754f4d` and orphaned by `1aaab2887`; only `peerFromUnknown` and `peerUnknownChip` are still referenced (`PeerSenderChip.tsx:31,33`). Delete the unused pair.

### m4 — Sender chip is always a link, even when the source session is gone

`web/src/components/AssistantChat/messages/PeerSenderChip.tsx:43-59` renders a navigating button whenever an id is present. Provenance is validated at delivery time only, so a deleted or since-inaccessible source session yields a chip that navigates to a dead route. Fix: fall back to the non-link `<span>` branch when the id is not in the session list.

### m5 — `sourceName` is a delivery-time snapshot with no note saying so

`hub/src/web/routes/messages.ts:37-41` freezes the source session's name into the row. Session titles change often, so old rows will disagree with the live title while the link resolves to the current session. This may well be the intent (historical accuracy), but nothing says so. Fix: one comment, or prefer the live title from the session list and fall back to the snapshot.

### m6 — Third definition of "what a session id looks like"

`cli/src/modules/pingPeer/pingPeer.ts:25-26` hand-rolls a UUID regex; the session-create boundary already enforces `z.string().uuid()` (`shared/src/apiTypes.ts:28`) and `@hapi/protocol/sessionCitation` owns prefix normalization. Correct today, but it is a second source of truth and it silently drops provenance if hub ids ever stop being UUIDs. Fix: export one validator from `shared` and use it in both places.

### m7 — The mapping the chip depends on is untested

`web/src/lib/assistant-runtime.ts:436-462` is the only path from hub `meta` to `metadata.custom.sentFrom` / `custom.peer`, and it has no test. The new tests cover the pure helpers (`web/src/chat/peerDelivery.test.ts`) and the chip in isolation (`PeerSenderChip.test.tsx`), so a regression in the middle layer would be silent. Fix: one `toThreadMessageLike` case asserting a `user-text` block with peer meta produces `custom.sentFrom === 'peer'` and the source fields.
