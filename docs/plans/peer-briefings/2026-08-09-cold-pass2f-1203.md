## Blocker

### B1 - resume mint tag still recoverable by a same-UID sibling via `/proc/<pid>/fd/3` during bootstrap awaits

**Evidence:** `cli/src/runner/run.ts:674-694`; `cli/src/agent/peerSessionTagFd.ts:15-56`; `cli/src/agent/sessionFactory.ts:321-335`; hub mint gate `hub/src/socket/handlers/cli/index.ts:95-108`.

The tag is no longer in `process.env` / `/proc/<pid>/environ`. That part of the claimed fix is real. The runner writes the secret onto an inherited pipe at stdio fd 3 and exports only `HAPI_PEER_SESSION_TAG_FD=3` (the fd number). The CLI is supposed to read once and close.

`bootstrapExistingSession` does **not** consume that fd first. It awaits `ApiClient.create()`, `getMachineIdOrExit()`, `getOrCreateMachine()`, and `getSession()` **before** `consumePeerSessionTagFromFd()`:

```321:335:cli/src/agent/sessionFactory.ts
    const api = await ApiClient.create()
    const machineId = await getMachineIdOrExit()

    await api.getOrCreateMachine({
        machineId,
        metadata: buildMachineMetadata()
    })
    // ...
    const sessionInfo = await api.getSession(options.sessionId)
    const sessionTag = options.sessionTag?.trim() || consumePeerSessionTagFromFd()
```

During that network window the unread pipe remains open on the victim CLI. On this host (`ptrace_scope=0`), a same-UID non-descendant opened `/proc/<victim>/fd/3` and read the full tag; the victim's later read got empty. The env advertises the exact fd number, so the sibling does not need to scan descriptors.

With the stolen tag + the shared namespace CLI token, the sibling opens `/cli` with `{ sessionId: victim, sessionTag: stolen }` and receives a minted capability (`peerCapabilityOnConnect.test.ts` documents that path as intentional when the tag matches). `POST /cli/sessions/<victim>/peer-messages` then stores incorrect attribution to the victim.

This is the same incorrect-attribution outcome as pass 2e-alt B1, with a shorter but still practical window (hub RTTs, not process lifetime). The RFC/orchestrator kill line is provenance correctness, not "secret left environ."

**Suggested fix:** call `consumePeerSessionTagFromFd()` synchronously at process entry for resume (or as the first statement of `bootstrapExistingSession`, before any `await`). Prefer reading into a local, closing the fd, then doing network work. Add a regression test that models a same-UID non-descendant reading `/proc/<pid>/fd/N` during a delayed consume and asserts the victim still owns the only copy (or that mint fails closed for both if the race is lost). Moving the secret off environ without early consume does not close B1.

Confidence: 95%.

## Friction (steelman)

Opposite case: "same-UID + `ptrace_scope=0` already owns the box; fd race is noise." Kill criterion for that steelman: if the estate treats same-UID siblings as mutually trusted, amend the RFC and stop spending cold passes on sibling mint theft. Until then, a multi-await window with an advertised fd number is not an acceptable residual of B1 - it is the same incorrect-attribution class with a stopwatch instead of a lifetime lease.

Cheapest falsification after a fix: resume two sessions under one UID; from A, during B's startup, `open('/proc/<B>/fd/3')` and assert either (a) read fails / empty because B already consumed, or (b) B's mint fails closed and A cannot obtain a working victim capability.
