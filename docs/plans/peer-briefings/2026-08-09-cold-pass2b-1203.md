## Blocker

### B2 - Keep the assistant-ui selector referentially stable

**Evidence:** `web/src/components/AssistantChat/messages/UserMessage.tsx:36-51`; installed hook contract at `node_modules/@assistant-ui/store/src/useAuiState.ts:10-17,42-46`.

`HappyUserMessage` now returns a newly allocated object from `useAuiState` on every snapshot read. The installed hook passes that value directly through `useSyncExternalStore` and compares it with `Object.is`; its own contract explicitly says object/array literals are unsupported because they change on every read. This affects every rendered user message, not only peer rows, and can produce the React uncached-snapshot loop / maximum-update-depth failure as soon as the chat surface renders.

**Suggested fix:** select stable primitives separately (`sentFrom`, `sourceSessionId`, `sourceName`) or select an existing stable metadata reference and derive the display model outside the hook. Add a `HappyUserMessage` render test with a peer row so the current isolated `PeerSenderChip` tests cannot miss the integration failure.

Confidence: 99%.

## Major

### M2 - Give resumed wrapped sessions a valid capability

**Evidence:** `cli/src/agent/sessionFactory.ts:325-347`, `hub/src/web/routes/cli.ts:249-264`, `cli/src/claude/utils/startHappyServer.ts:301-306`, `cli/src/modules/pingPeer/pingPeer.ts:576-593`.

Every `bootstrapExistingSession` path loads its HAPI session through `GET /cli/sessions/:id`, but that route returns no `sessionCapability`. The resulting `ApiSessionClient` therefore holds `null`; MCP `ping_peer` supplies the source id without a capability, and `pingPeer` deliberately falls back to the unattributed web-JWT route. This applies to resumed Claude, Codex, Cursor, Pi, OpenCode, Agy, Copilot, Grok, and Kimi sessions. The receiver sees `From: peer (unattributed)` and cannot route a reply, despite the sender being a wrapped session with `HAPI_SESSION_ID`.

**Suggested fix:** provide a capability recovery/rotation path authenticated by the live source-session channel, or persist a per-session secret that a legitimate resume can recover. Do not simply return the capability from the namespace-token GET route: any namespace-token holder can GET any same-namespace session, which would reopen B1. Add an end-to-end bootstrap-existing test proving a resumed session attributes as itself and cannot obtain another session's capability.

Confidence: 99%.
