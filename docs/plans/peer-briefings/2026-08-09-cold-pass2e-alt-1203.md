## Blocker

### B1 - the resume tag is still readable by a same-UID sibling, now from `/proc/<pid>/environ`

**Evidence:** `cli/src/runner/run.ts:644-653` and `cli/src/runner/run.ts:676-684`; `cli/src/agent/sessionFactory.ts:18-24,339`; `hub/src/socket/handlers/cli/index.ts:95-107`; `hub/src/sync/syncEngine.ts:2800,2814-2815`.

Pass 2d B3 was that the create-time tag and the bearer capability lived in a mode-0600 file under shared `HAPI_HOME`, readable by any process with the same effective UID. The on-disk store is gone on this tip, which is a genuine improvement. The tag it replaced the file with, however, is delivered to the resumed CLI through the process environment, and `delete process.env[HAPI_PEER_SESSION_TAG]` does not remove it from the kernel's copy.

`consumePeerSessionTagFromEnv()` deletes the key from the JavaScript `process.env` object. On Linux the kernel serves `/proc/<pid>/environ` from the original `mm->env_start..env_end` stack region captured at `execve`; runtime `unsetenv` rewrites the pointer array in the heap and never touches that region. The tag therefore stays readable for the whole lifetime of the session CLI process, which is the whole lifetime of the session.

A runtime check on this machine confirmed all three links:

- Inside the process, after `delete process.env[...]`, `process.env` returned `null` but `/proc/self/environ` still contained `HAPI_PEER_SESSION_TAG=victim-session-tag-1234`.
- A separate same-UID process that was **not** a descendant read `/proc/<pid>/environ` and recovered the same value.
- `/proc/sys/kernel/yama/ptrace_scope` is `0` on this host, which is the kernel default and the setting on the estate machine this work is for.

The chain from there is short and is proven by the diff's own tests: a sibling already holds the namespace CLI token (it is on disk under the same UID; `exportHapiHubAuthEnv` deliberately not exporting it into agent env does not change that a fresh `hapi` re-reads settings). With the recovered tag it opens a `/cli` socket with `{ sessionId: victim, sessionTag: victim }`, and the handler mints the victim's capability - which is exactly what `hub/src/socket/handlers/cli/peerCapabilityOnConnect.test.ts:113-133` asserts as correct behavior for a matching tag. `POST /cli/sessions/<victim>/peer-messages` then stores the victim's id as the source of the delivery.

The scope is narrower than pass 2d: the create path generates `sessionTag` with `randomUUID()` in memory and never puts it in env (`cli/src/agent/sessionFactory.ts:187,215`), so only runner-resumed sessions are exposed. The exposure is also Linux-specific and depends on `ptrace_scope=0`; at `ptrace_scope=1` (the Ubuntu default) only descendants of the victim CLI can read it, and those are legitimately that session. That is a real reduction in blast radius, but it is a configuration-dependent one, and the RFC kill criterion is not "hard on some hosts."

The comment at `cli/src/agent/sessionFactory.ts:335-337` ("cleared before agent spawn") and at `cli/src/runner/run.ts:645-646` ("so it is not a durable shared-disk secret") both overstate what the delete achieves and should not survive into an upstream PR in their current form.

**Suggested fix:** hand the tag to the resumed CLI over a channel that is not inherited and not exposed in `/proc` - the runner already has an authenticated machine socket to the hub and a live channel to the child, so passing it on stdin at startup, or having the runner hold it and proxy the mint, both avoid the environment entirely. If the environment really is the only practical channel, the design needs an explicit scope statement that same-UID siblings on `ptrace_scope=0` hosts are trusted, and the RFC's no-incorrect-attribution claim and kill criterion 4 need amending to match. Add a test that models two runner-resumed sessions under one OS user and asserts A cannot recover B's tag.

Confidence: 95% (the 5% is the `ptrace_scope` dependency, not the mechanism).

## Major

### M1 - wrapped `hapi ping-peer` hard-fails on every non-Linux host

**Evidence:** `cli/src/api/peercred.ts:31-35`; `cli/src/api/processDescendant.ts:36`; `cli/src/commands/pingPeer.ts:183-197`; `cli/src/api/peerDeliverBroker.ts:99-107`.

`readUnixPeerCredentials` hardcodes `SOL_SOCKET = 1` and `SO_PEERCRED = 17`. Those are Linux values (on x86-64 / arm64 specifically). macOS uses `SOL_SOCKET = 0xffff` and has no `SO_PEERCRED` at all - the nearest equivalents are `LOCAL_PEERCRED` at `SOL_LOCAL` and `getpeereid()`, and neither returns a pid. The `getsockopt` call therefore returns non-zero, the reader returns `null`, and `handleConnection` fails closed at `peerDeliverBroker.ts:100`. Even if the constants were corrected, `isProcessDescendant` reads `/proc/<pid>/stat`, which does not exist on macOS.

`cli/src/commands/pingPeer.ts:186-192` routes on `HAPI_SESSION_ID` alone, which is exported on every platform, so there is no fallback: inside any wrapped session on macOS, `hapi ping-peer` now returns `auth_failed` where it previously delivered. On Windows the broker's `listen()` on a filesystem path is not a named pipe, so `ensurePeerDeliverBroker` swallows the error (`cli/src/api/apiSession.ts:352-355`), the env var is never set, and the child fails with "peer deliver broker is unavailable."

MCP `ping_peer` is unaffected because it delivers in-process, so the damage is confined to the CLI command - but that command is the documented shell-tooling path (`cli/src/agent/hapiSessionEnv.ts:20-22`) and upstream HAPI is macOS-first.

**Suggested fix:** platform-gate the broker requirement. On hosts where peer credentials cannot be read, either fall back to the MCP-equivalent in-process path or keep the pre-existing unattributed send rather than failing the command outright; a `getpeereid`-based uid check plus a documented "no pid, no descendant proof" downgrade is a reasonable middle. Add a test that asserts behavior when `readPeerCred` returns `null` at the *command* level, not only at the broker level.

Confidence: 90%.

### M2 - terminal-resumed sessions lose peer messaging entirely

**Evidence:** `cli/src/commands/resume.ts:67-73`; `cli/src/agent/sessionFactory.ts:326,339,361-363`; `cli/src/claude/utils/startHappyServer.ts:301-307`; `cli/src/commands/pingPeer.ts:186-192`; `cli/src/api/apiSession.ts:342-356`.

Only the hub-to-runner spawn path carries `peerSessionTag` (`hub/src/sync/syncEngine.ts:2814-2815`). `hapi resume` dispatches locally with `startedBy: 'terminal'` and `existingSessionId` set, so `bootstrapExistingSession` runs with `consumePeerSessionTagFromEnv()` returning `undefined`. The socket handshake then omits `sessionTag`, the hub declines to mint, `sessionCapability` stays `null` forever, and `ensurePeerDeliverBroker` is never reached.

Both peer paths then fail permanently for that session, not transiently:

- MCP `ping_peer` waits 5s in `waitForPeerSessionCapability`, gets `null`, and throws `auth_failed`.
- `hapi ping-peer` sees `HAPI_SESSION_ID`, calls `requestParentPeerDeliver`, finds no broker env, and throws `auth_failed`.

Before this diff both worked, unattributed. Fail-closed is the right instinct when a session *can* attribute and the proof is merely late, but this is a whole class of sessions that can never attribute, so the failure is permanent rather than a race. The user-visible result is that resuming a session from the terminal silently removes its ability to message peers at all.

**Suggested fix:** give the local resume path the same tag plumbing the runner path has (`resolveLocalResumeTarget` already reads the session row hub-side and could return the tag over the authenticated CLI channel), or distinguish "attribution unavailable for this session" from "attribution not ready yet" and let the former fall back to unattributed with a warning. Add a terminal-resume test at the command level covering both peer paths.

Confidence: 95%.

### M3 - the broker socket path is predictable and rebindable by a same-UID sibling

**Evidence:** `cli/src/api/peerDeliverBroker.ts:56,63-74,158-162`; client side `cli/src/api/peerDeliverBroker.ts:196-240`.

`defaultBrokerSocketPath` is `${XDG_RUNTIME_DIR}/hapi-peer-deliver/${sessionId}.sock` - fully derivable from a session id, which is listable by any namespace-token holder. `start()` itself demonstrates the primitive: it unlinks whatever is at the path and binds its own listener. Nothing stops a sibling process from doing the same afterwards, and `requestParentPeerDeliver` performs no check on who is answering - it connects, writes the message, and trusts the reply.

A runtime check confirmed the mechanic: after a second listener unlinked the bound path and rebound it, a fresh `connect()` resolved to the second listener, which received the request body and returned a well-formed `{ ok: true }`.

The consequence is not a stolen capability - the sibling still cannot mint or send as the victim. It is that the victim's outgoing peer message text goes to the sibling instead of the hub, and the victim's agent is told the delivery succeeded. Within the same-UID sibling model this diff explicitly sets out to defend, silent interception plus a false success is squarely in scope: the delivery is unauthenticated in the direction the diff did not harden.

**Suggested fix:** make the client verify the server rather than only the reverse. The child can read peer credentials on its own end of the connection and require that the listening pid is one of its ancestors, which mirrors the server-side check and needs no new secret. An unguessable random suffix in the socket path passed through the broker env var raises the cost but does not close it on its own, given B1.

Confidence: 90%.

### M4 - the mint gate now travels to the runner over the spawn RPC

**Evidence:** `hub/src/sync/syncEngine.ts:2800,2814-2815`; `hub/src/sync/rpcGateway.ts:179-210`.

`spawnSession` now carries `peerSessionTag` in the RPC payload to the target machine. The tag is the sole gate on capability minting, so the set of parties that can obtain it has grown from "the hub and the owning CLI" to "the hub, the owning CLI, and whoever is servicing that machine's spawn RPC." Machine RPC handlers are registered over sockets authenticated by the shared namespace token, which is the same credential the rest of this review treats as available to every session on the host.

I did not verify whether the RPC registry lets a second same-namespace socket claim or shadow an existing machine's `spawn-session` method, so I am not calling this reachable as written - but the diff moves a newly-security-critical secret onto a channel whose authentication was designed when it carried only spawn parameters. That warrants an explicit look before upstream rather than after.

**Suggested fix:** confirm that machine-scoped RPC method registration cannot be claimed or shadowed by another socket holding the same namespace token, and state that assumption in the RFC. If it can, the tag must not travel this way.

Confidence: 80% (high on the exposure widening, low on whether it is presently reachable).

## Minor

### m1 - the real peer-credential reader has no test coverage

`cli/src/api/peerDeliverBroker.test.ts:50,96` inject a fake `readPeerCred` in both cases, and the CLI suite runs under Vitest where `require('bun:ffi')` throws and `readUnixPeerCredentials` returns `null` through its own catch (`cli/src/api/peercred.ts:46-48`). The entire authorization primitive the Blocker-adjacent design rests on is therefore exercised only through a stub. The hardcoded constants at `peercred.ts:31-32` are also correct only for x86-64 / arm64 Linux; other Linux architectures use different values for both `SOL_SOCKET` and `SO_PEERCRED`. Those cases do fail closed - a wrong optname returns `-1`, and a short read leaves `pid` at `0` or `1`, both rejected - so this is a coverage and portability gap rather than a hole.

Confidence: 100%.

### m2 - capabilities never expire and source-session liveness is not checked

`mintPeerSessionCapability` (`hub/src/web/peerCapability.ts:15-21`) is a deterministic HMAC over `sessionId` with no nonce, issue time, or expiry, so a given session's capability is the same value forever and stays valid until the hub JWT secret rotates. `POST /cli/sessions/:id/peer-messages` (`hub/src/web/routes/cli.ts:313-330`) checks `target.session.active` but never `source.session.active`. A capability retained from a long-finished session can still produce deliveries attributed to it.

Confidence: 95%.

### m3 - `sourceName` is a self-settable title rendered as the primary identity

`resolvePeerMetaFromSourceSession` (`hub/src/web/routes/messages.ts:43-60`) snapshots `metadata.name` from the store. Session titles are settable by the session itself, so one session can adopt another's display name. The stored `sourceSessionId` remains authoritative, but the rendered identity leads with the name in both surfaces: the agent-facing line is `From: /sessions/<id> (<name>)` (`cli/src/utils/attachmentFormatter.ts:36-44`), and the web chip labels with `@<name>` and surfaces the id only in the tooltip (`web/src/lib/sessionMentionChip.ts:9-11`, `web/src/components/AssistantChat/messages/PeerSenderChip.tsx`). The agent-facing line is also a prefix on peer-controlled body text, and estate convention has agents opening pings with their own `From:` line, so a receiving agent sees two and has no stated rule for which wins.

Confidence: 85%.

## Nit

### n1 - wrapped `hapi ping-peer` loses its progress output

`cli/src/commands/pingPeer.ts:186-197` passes `onProgress` only on the outside-session branch. Inside a wrapped session the broker path drops it, so the resolve / wait-active / resume lines that the same command prints outside a session disappear, and a long resume looks like a hang.

Confidence: 100%.
