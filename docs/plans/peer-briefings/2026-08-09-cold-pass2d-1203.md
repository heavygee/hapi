## Blocker

### B3 remains open - shared HAPI_HOME lets session A steal session B's capability

**Evidence:** `cli/src/api/peerSessionCredentialStore.ts:23-40`; `cli/src/agent/sessionFactory.ts:342-370`; capability use at `hub/src/web/routes/cli.ts:301-315`.

The socket mint now requires the matching create-time tag, but the new resume store writes both that tag and the bearer capability to the common `<HAPI_HOME>/peer-session-credentials/<sessionId>.json`. Mode `0600` excludes other Unix users; it does not isolate HAPI agent processes running under the same Unix account. Session A can list B's session id, read B's JSON file directly, then either present B's stolen capability to `POST /cli/sessions/:B/peer-messages` or present B's stolen tag to the socket mint. The tag gate therefore moves the secret from the namespace-token channel to a sibling-readable file without closing the same-session forgery.

An adversarial runtime proof created B's credential through `savePeerSessionCredentials`, then read it as a second same-UID process. The file was mode `600`, and both `stoleVictimTag` and `stoleVictimCapability` were `true`. Linux defines `0600` as owner read/write; every sibling process with that effective UID is the owner for permission checks.

**Suggested fix:** do not persist a reusable source-session bearer or mint proof in a shared filesystem location readable by wrapped agents. Keep ownership proof behind a session-scoped parent/runner broker or another boundary the agent process cannot read, and have the hub derive the source from that authenticated channel. Add an adversarial test that models two wrapped sessions under the same OS user and proves A cannot read or use B's resume proof. If same-UID sibling agents are intentionally trusted, the RFC's no-forged-provenance claim and kill criterion need an explicit scope change instead.

Confidence: 100%.

## Major

### M4 - wrapped `hapi ping-peer` still silently sends unattributed

**Evidence:** `cli/src/modules/pingPeer/pingPeer.ts:576-603`; call site `cli/src/commands/pingPeer.ts:180-185`.

The RFC contract covers both `ping_peer` and `hapi ping-peer`: inside a wrapped session they must derive the source from `HAPI_SESSION_ID`, while only an out-of-session invocation may be unattributed. The MCP handler now waits for the capability and fails closed, but the standalone command passes neither `authenticatedSourceSessionId` nor `sessionCapability`. `pingPeer` therefore always takes `sendUnattributedPeerMessage`, even when the child command inherited `HAPI_SESSION_ID` from a resumed wrapped session. This is a silent downgrade on every wrapped CLI invocation, including the first ping after resume, and the existing CLI test suite has no command-level provenance case.

**Suggested fix:** give the standalone command a secure way to obtain the current session's capability from the active session-scoped parent/broker, then pass both source id and capability. If `HAPI_SESSION_ID` is set but authenticated proof is unavailable, fail closed with `auth_failed`; reserve unattributed delivery for processes with no session context. Do not solve this by reading the sibling-readable credential file from B3. Add command-level inside-session, delayed-proof, missing-proof, and outside-session tests.

Confidence: 99%.
