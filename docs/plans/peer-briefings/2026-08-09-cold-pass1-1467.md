## Major

**M1. Ingested ledger rows survive session deletion.**
`hub/src/store/index.ts:510` - `related_session_id TEXT` with no FK; `hub/src/store/sessions.ts:695-700` - delete is a bare `DELETE FROM sessions`, and messages/scratchlist disappear only through FK cascade. Ingested `work_ad` rows carry the agent's own summary prose and outlive the session forever, so "delete session" no longer means the summary text is gone. Either behaviour is defensible (append-only audit ledger vs. user-facing delete), but the PR does not record a decision or test one.
Fix: either delete namespace-scoped rows in the session delete path, or state in the PR that the ledger is append-only audit and deliberately survives, with a test pinning it.

**M2. `expires_at` is never populated and nothing reaps or filters it.**
`hub/src/sync/workGraphNotifyIngest.ts:96-129` accepts an `expiresAt` param that `ingestNotifySummaryFromMessage` (`:152-158`) never supplies; `hub/src/store/workGraph.ts:234-248` lists without an expiry filter; the `idx_events_namespace_expires` index (`hub/src/store/index.ts:520-521`) is written by nobody and read by nobody. RFC § WorkAdvertisement says a missing status "leaves a work ad `unknown`, and eventually `stale` via `expires_at`" - with no expiry there is exactly one permanent row per assistant turn with a footer, forever, and `stale` can never be derived.
Fix: set `expires_at = ts + TTL` in `buildWorkAdFromNotify`, or drop the param plus index and say in the PR that staleness is P4.

**M3. The message timestamp is accepted and then dropped.**
`hub/src/sync/workGraphNotifyIngest.ts:68` declares `ts` on `NotifyIngestInput` and the function body never reads it, so every row gets `Date.now()` (`hub/src/store/workGraph.ts:150`). `WorkGraphStore.insertEvent` (`hub/src/store/workGraphStore.ts:26-28`) also drops the `options` passthrough that `insertWorkGraphEvent` already supports. This matters because `message-received` is not only realtime: transcript imports replay historical messages through the same entry point (`hub/src/web/routes/codexDesktop.ts:1383`, `hub/src/web/routes/piSessions.ts:129-136`), so imported footers get ingest-time timestamps and `ORDER BY ts DESC` (`hub/src/store/workGraph.ts:241-246`) returns them in the wrong order.
Fix: `insertEvent(namespace, input, options?)` and pass `{ ts: input.ts }`.

**M4. The RFC's project-scoped query is not representable in the schema this PR freezes.**
RFC § WorkAdvertisement: work ads are "both session-scoped and project-scoped ... both must be indexed. A single fleet-wide pass over current ads is a first-class query, not a scan." Here `project` lands only in the `tags` JSON array (`hub/src/sync/workGraphNotifyIngest.ts:84-90`) and inside `payload_json`; there is no column, no index, and the query route supports `related_session_id` only (`hub/src/web/routes/workGraph.ts:47-61`). Since this PR is deliberately laying the A0 substrate for #1374, P1 will have to migrate the table again to get there.
Fix: add `project TEXT` plus `idx_events_namespace_project_ts` now and populate from `notify.project`, or say explicitly in the PR that project indexing is deferred and #1374 owns that column.

## Minor

**m5. Capture delays chat delivery.** `hub/src/sync/syncEngine.ts:473-493` runs two synchronous SQLite statements before `this.eventPublisher.emit(event)` at `:496`. Ledger capture has no reason to sit in front of the SSE broadcast. Fix: move the block below the emit.

**m6. No size cap on ledger writes.** `hub/src/web/routes/workGraph.ts:18-45` accepts arbitrary `payload_json` and `artifact_refs` from any authenticated client. The repo already uses `bodyLimit` for voice (`hub/src/web/routes/voice.ts:517`), and the RFC § ArtifactRef is explicit that refs are "handles, never payloads ... otherwise the ledger becomes both a bloat and a leak surface" - nothing in code enforces that. Fix: `bodyLimit({ maxSize: 64 * 1024 })` on both POSTs.

**m7. `principalMatchesAuthenticatedOwner` is not a tenant boundary.** `uid` is a single hub-wide owner id (`hub/src/config/ownerId.ts:22`) handed to every namespace (`hub/src/web/routes/auth.ts:35,56`, `hub/src/web/routes/bind.ts:50`), so every authenticated caller in every namespace passes the check at `shared/src/workGraph.ts:119-128`. It catches typos, not impersonation; namespace is the only real isolation. No code fix needed - document it so P2 handoffs do not treat principal as authorization.

**m8. `hubOwnerUserId` silently defaults to `'1'`.** `hub/src/sync/syncEngine.ts:193`. Any SyncEngine constructed without `setHubOwnerUserId` writes rows attributed to an owner that does not exist on that hub, and an HTTP client could never reproduce or match them. Fix: constructor argument, or leave it `null` and skip ingest with a single warn.

**m9. `principal_json` is parsed unguarded.** `hub/src/store/workGraph.ts:105` uses a raw `JSON.parse` while every other JSON column goes through the safe helpers at `:65-81`. One corrupt row throws out of `listByRelatedSession` and 500s the entire list. Fix: reuse `parseJsonUnknown` with a fallback.

**m10. Principal id falls back to the session id.** `hub/src/sync/workGraphNotifyIngest.ts:105` - when the footer omits `agent`, `principal.id` becomes a session id, mixing two identifier spaces in one field that later phases will query. Fix: `session:${sessionId}`.

**m11. The `/health` capability test asserts against a copy.** `hub/src/web/routes/workGraph.test.ts:23-27` re-declares the handler from `hub/src/web/server.ts:237-241` and mounts its own auth middleware, so neither the shipped health body nor the real `/api` mount point is covered - a regression in `server.ts` passes this suite. Fix: assert through `createWebApp`, or export a `buildHealthBody()` both sides use.

**m12. Nothing tests the syncEngine wiring.** Every ingest test calls `ingestNotifySummaryFromMessage` directly (`hub/src/sync/workGraphNotifyIngest.test.ts`), so the `'message' in event` guard, the session lookup, the namespace source, and the flavor tag at `hub/src/sync/syncEngine.ts:475-493` are untested. That block is where the "display never gates capture" invariant actually lives, and the test named for that invariant (`:175-193`) only exercises the pure helper. Fix: one test that fires a `message-received` event through the engine and asserts a row appears.
