## Blocker

### B1 - Bind the source id to a session credential, not the namespace token plus a path claim

**Evidence:** `hub/src/web/routes/cli.ts:73-94`, `hub/src/web/routes/cli.ts:294-325`, `hub/src/web/routes/cli.test.ts:322-347`, `cli/src/modules/pingPeer/pingPeer.ts:570-582`.

The new CLI route does not authenticate the caller as the source session named in `:id`. Its middleware validates the shared `CLI_API_TOKEN` and records only the token namespace. The handler then accepts `c.req.param('id')` as the source as long as that session exists in the namespace. The route test demonstrates the problem: a request with ordinary `authHeaders()` chooses an arbitrary `sourceId` in the path and is stored as that source. There is no caller identity to compare with the path.

Moving the same client-controlled value from the body to the URL does not bind it to `ApiSessionClient.sessionId`. Any holder of the namespace CLI token can call `/cli/sessions/<victim>/peer-messages` and forge the victim's provenance. This still meets the RFC stop condition: "any claim not bound to an authenticated source-session channel" (`docs/plans/2026-08-03-a2a-control-plane-rfc.md:140-143`).

**Suggested fix:** deliver attributed peer messages over a channel whose credential is scoped to one session, and have the hub derive the source from that authenticated channel. A Socket.IO event can work only after the hub validates and stores a session-bound identity at connection time; the current shared token plus client-supplied handshake/path id is not sufficient. Alternatively mint a per-session bearer capability during session creation and require it on this route. Add an adversarial test where a credential for session A attempts to attribute as session B and is rejected or stored unattributed.

Confidence: 98%.

## Major

### M1 - Route Pi messages through the peer provenance formatter

**Evidence:** `cli/src/utils/attachmentFormatter.ts:35-67`, `cli/src/pi/runPi.ts:743-768`.

`formatUserMessageForAgent` now exposes `From: /sessions/<id>` to the receiving agent paths changed in this PR, but Pi has its own prompt preparation path and was not updated. `runPi` passes `message.content.text` and attachments into `preparePiUserMessage` without `message.meta`, so an attributed peer row reaches Pi as only the original body. Pi therefore cannot observe `sourceSessionId` or reply to the sender, leaving the pass-1 M1 and the RFC's agent-visibility kill criterion unresolved for a supported flavor.

**Suggested fix:** thread `message.meta` through Pi prompt preparation and apply the peer annotation while preserving Pi's first-line slash/skill command requirement. Add a test that an attributed peer message produces a Pi RPC prompt containing `/sessions/<sourceId>`, plus an unattributed-peer case.

Confidence: 99%.
