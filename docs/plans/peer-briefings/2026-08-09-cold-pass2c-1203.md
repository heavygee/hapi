## Blocker

### B3 - A namespace token can mint and steal another same-namespace session's capability

**Evidence:** `hub/src/socket/server.ts:113-122`; `hub/src/socket/handlers/cli/index.ts:92-101`; `hub/src/web/routes/cli.ts:294-310`.

The `/cli` Socket.IO middleware authenticates only the shared namespace token. The new recovery path then trusts the caller-provided `handshake.auth.sessionId`; if that id resolves in the namespace, it emits the session's HMAC capability. A wrapped session already holds the namespace token, so it can open another `/cli` socket naming any known same-namespace victim id, receive the victim capability, and use `POST /cli/sessions/:victim/peer-messages` to forge peer deliveries as that victim. This directly meets RFC kill criterion 4.

The new "foreign session id" test covers an id for which access does not resolve. It does not cover the adversarial case: two existing sessions in the same namespace. A runtime harness using the normal handler inputs reproduced the leak and received `peer-capability` for a caller-selected existing victim id.

**Suggested fix:** do not deliver a session bearer capability over a socket authenticated only by the namespace token plus caller-selected id. Bind session-scoped socket authentication to proof unavailable to sibling sessions, or replace this bearer recovery design. Add a two-session test proving session A cannot obtain session B's capability even though both share a namespace token.

Confidence: 100%.

## Major

### M3 - A resumed session's first `ping_peer` can silently lose attribution

**Evidence:** `cli/src/api/apiSession.ts:286-295,313-325`; `cli/src/claude/utils/startHappyServer.ts:294-307`; `cli/src/modules/pingPeer/pingPeer.ts:580-592`.

Resume intentionally initializes `sessionCapability` to `null`, starts Socket.IO asynchronously, and returns without waiting for `peer-capability`. The MCP handler snapshots `client.getPeerSessionCapability()` when `ping_peer` starts. If the agent invokes the tool before the socket event arrives, `pingPeer` takes the unattributed web-JWT fallback. A capability arriving during the request cannot repair that delivery because the null value was already copied into the options object.

This is a normal startup race, not just a disconnected-hub case. The new unit test establishes the pre-event null state but only verifies later storage; no test invokes `ping_peer` during that window. The receiver then gets `From: peer (unattributed)` and cannot reply to the wrapped source session.

**Suggested fix:** make capability readiness awaitable and have attributed callers wait or fail explicitly instead of silently downgrading when `authenticatedSourceSessionId` is present. Add a delayed-`peer-capability` test with an immediate resumed-session `ping_peer`.

Confidence: 95%.
