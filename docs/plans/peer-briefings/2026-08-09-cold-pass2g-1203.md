## Blocker

### B1 - resume mint tag still stealable via `pidfd_getfd` before module-load drain completes

**Evidence:** `cli/src/agent/peerSessionTagFd.ts:27-33,90-92`; `cli/src/index.ts:3-5`; `cli/src/runner/run.ts:670-693`; runtime on this host (`ptrace_scope=0`).

**What the tip fixed (verified):**

- `drainPeerSessionTagFdEarly()` runs on `peerSessionTagFd` module load; `consumePeerSessionTagFromFd()` is the first statement of `bootstrapExistingSession` before any `await`.
- `cli/src/index.ts` side-effect-imports `peerSessionTagFd` first.
- Live harness: Bun runner stdio fd 3 is a **socketpair** (`socket:[…]`). After early drain, attacker `pidfd_getfd` reads empty / EAGAIN and the victim owns the tag. Delayed-consume (pass2f shape) still loses the tag to `pidfd_getfd` and the child reads empty. So the multi-await / hub-RTT window pass2f filed is **gone**.

**What is not closed:**

Bun/Node `stdio: 'pipe'` is a socketpair. Plain `open('/proc/<pid>/fd/3')` returns `ENXIO` (sockets are not reopenable through procfd). Pass2f's stated `/proc/fd` **open** path is therefore imprecise for the real runner spawn. The reachable same-UID vector on this host is `pidfd_open` + `pidfd_getfd` (PTRACE_MODE_ATTACH; allowed at `ptrace_scope=0`).

Aggressive poll from process start against the real `peerSessionTagFd` module-load drain:

- Attacker got the full tag at `t_ms≈1` via `pidfd_getfd`.
- Victim printed `TAG=undefined` (mint skipped / fail-closed for the victim).
- Attacker still holds the create-time tag + shared namespace CLI token → can open `/cli` as the victim and mint (`peerCapabilityOnConnect.test.ts` documents that path). Incorrect attribution survives.

So: "sync drain before await" closed the stopwatch pass2f measured; it did not close the class. The secret still sits on an inherited fd advertised by `HAPI_PEER_SESSION_TAG_FD=3` until the first JS module side-effect runs. That window is short and racey, and we won it with a trivial poll loop.

**Suggested fix:** stop putting the mint tag on a child-inherited fd. Prefer runner-side mint over the already-authenticated machine/hub channel, then hand the child only a post-mint capability on a channel that is not readable by siblings before use - or spawn under `PR_SET_DUMPABLE=0` / tighter Yama so `pidfd_getfd` fails for non-descendants. If the estate instead decides same-UID + `ptrace_scope=0` siblings are mutually trusted, amend the RFC kill criterion and stop the cold-pass treadmill; memory is ptrace-readable after drain anyway.

Confidence: 95%.
